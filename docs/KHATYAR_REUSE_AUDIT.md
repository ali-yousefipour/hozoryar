# نقشه استفاده مجدد از خطیار در حضوریار

تاریخ بررسی: ۱۴۰۵/۰۸/۱۰ · مرجع: `ali-yousefipour/khatyar` در commit `582241526a678af67a18126c5fb16a08ded56565`.

## اصل تصمیم

هر قابلیت ابتدا با منبع موجود خطیار تطبیق داده می‌شود. کدهای آزمایش‌شده و مستقل از پروژه در اولویت استفاده مجدد هستند. **کدهای وابسته به جداول، تنظیمات یا کاربران سراسری خطیار نباید مستقیم به حضوریار چندشرکتی کپی شوند.**

حضوریار فعلاً سرور Node.js/SQLite دارد، در حالی که هسته اصلی خطیار PHP/MySQL است. به همین دلیل کپی فایل PHP در مسیر Node.js قابلیت اجرایی ایجاد نمی‌کند. برای موتور کارکرد، دو گزینه اصولی داریم: (الف) مهاجرت یکپارچه سرویس منابع انسانی به PHP و استفاده از همان کلاس‌ها، یا (ب) نگه‌داشتن سرور Node.js و انتقال قرارداد/تست‌های رسمی محاسبات به موتور واحد Node.js. **تا انتخاب و آزمون مسیر واحد، ساخت موتور سومی ممنوع است.**

## مواردی که نباید منتقل شوند

- جدول‌ها، مجوزها و APIهای تاکسی، خودرو، سرویس مدارس، شکایات تاکسیرانان، خطوط و شرکت‌های تاکسیرانی.
- کلیدها، شناسه‌های شرکت، مناطق و کاربران عملیاتی خطیار.
- تنظیمات `app_settings` که فرض می‌کند فقط یک سازمان وجود دارد.
- نسخه‌های تولیدشده `panel.bundle.js`، کش قدیمی نقشه، فایل‌های release و دارایی‌های استفاده‌نشده.
- راهکارهای قدیمی که تأیید TLS را خاموش می‌کنند یا عکس نامحسوس را بدون سیاست شفاف نظارت ثبت می‌کنند.

## قرارداد جداسازی چندشرکتی

۱. همه جدول‌های عملیاتی و snapshotها `company_id` دارند؛ برای جدول‌های مرجع ترکیبی `UNIQUE(company_id,...)` تعریف می‌شود.

۲. `company_id` فقط از نشست احرازشده سرور گرفته می‌شود؛ ورودی درخواست نباید اجازه تغییر محدوده داده بدهد.

۳. تنظیمات شیفت، سیاست کارکرد، درگاه پیامک، نشان، مناطق، نقش‌ها و مجوزها از تنظیمات همان شرکت خوانده می‌شوند.

۴. همه محاسبات و تأییدها باید تست دو شرکت با داده مشابه/همنام داشته باشند. واحد سنجش مالی باید از سناریوهای مرجع خطیار و تست‌های رگرسیون مشترک عبور کند.

۵. تغییر در موتور اصلی باید در یک ماژول واحد انجام شود؛ گزارش روزانه، گزارش ماهانه، صادرات و اپ اندروید حق داشتن فرمول جداگانه ندارند.

## ترتیب توسعه بدون دوباره‌کاری

1. **مرجع قواعد:** مشخص کردن همه ورودی/خروجی‌های `ShiftCalc`, `IranCalendar` و نمونه‌های مورد انتظار از تست‌های خطیار؛ انتخاب پشته واحد محاسبات و تست تطابق.
2. **چندشرکتی:** جداسازی schema و سیاست‌های درخواست/شیفت/تعطیلی/درگاه‌ها، آزمون جلوگیری از دسترسی متقاطع.
3. **خدمات مشترک:** یک API کارکرد و گزارش؛ یک API درخواست و گردش تأیید؛ یک API موقعیت و نظارت؛ یک آداپتور برای هر درگاه پیامک یا نقشه.
4. **تجربه کاربری:** توسعه پنل و اندروید با همان قرارداد API و رنگ‌های بنفش تأییدشده؛ فرم‌های شمسی و اجزای قابل استفاده مجدد.
5. **آمادگی انتشار:** migration، backup/restore، تست بار و امنیت، تست دستگاه، سپس build و امضا و استقرار.

## وضعیت فعلی حضوریار

`server/work.js` هنوز **موتور مقدماتی و غیرمالی** است و باید با خروجی‌های موتور خطیار تطبیق داده شود. در گام 0.3.1، قواعد سقف اضافه‌کار روزانه، تفکیک مازاد و شب‌کاری ۲۲–۶ با تست‌های مستقل افزوده شدند. در گام 0.4.0 مالکیت شیفت شب بر اساس روز ورود، بازه درون شیفت، تأخیر و تعجیل، پنجره‌های مجاز اضافه‌کاری و تقویم جلالی همراه تعطیلات دستی مستقل شرکت‌ها افزوده شدند؛ تقویم رسمی هنوز منبع تأییدشده ندارد. توسعه موازی منطق اضافه‌کاری و حقوق در اندروید یا وب ممنوع است. API گزارش مقدار `authoritative:false` را همراه منبع قواعد برمی‌گرداند تا استفاده برای حقوق قطعی اشتباهاً رخ ندهد.

در گام 0.5.0 بایگانی تغییرناپذیر گزارش ماهانه با کلید ترکیبی `(company_id,month)` و تراکنش نوشتاری افزوده شد، طبق الگوی `docs/work-month-finalization.md` خطیار. این مرحله **ماه میلادی و بایگانی غیرمالی** است؛ تبدیل به دوره شمسی، منبع رسمی تعطیلات و سازوکار تأیید مالی همچنان نیازمند کار مستقل و آزمون تطبیقی هستند.
